# Alembic downgrade() walk (FR-178, 2026-10-16)

Confirms, for the first time, whether any of the 19 Alembic migrations'
`downgrade()` actually reverses its `upgrade()` cleanly against a real
database. Until this check, `check_migrations.sh`'s "one Alembic head" CI
gate and every full-suite test run only ever exercised `alembic upgrade
head` — `downgrade()` had never been run against a real database (FR-178's
own `why`).

## Setup

Local Postgres 16 (`postgresql-16`, the same sandbox-native approach FR-177
drilled, not Docker), a fresh database (`filmrunner_migtest`), `alembic
upgrade head` first to confirm the forward path (clean, matches `main`'s
documented single head `7feea1cfc0e6`). Correctness was checked two ways at
every step: the command's own exit code, and an MD5 fingerprint of
`information_schema.columns` + `pg_indexes` + `pg_constraint` (via
`pg_get_constraintdef`) + `pg_enum` for the `public` schema, taken before a
downgrade and compared against the fingerprint after downgrading one step
and immediately upgrading back — not just "exit 0", a real schema diff.

## Result: 3 of 19 migrations have a broken or lossy `downgrade()`

16 of the 19 migrations downgrade and re-upgrade cleanly — fingerprint
identical before and after every one of those round trips. Three do not:

### 1. `0ea2247026ef` ("initial call sheet schema") — downgrade leaves 6 orphaned enum types

`downgrade()` drops every table cleanly (`\dt` after `alembic downgrade
base` shows only `alembic_version` left) but never drops the Postgres
`ENUM` types those tables' columns created: `production_status`,
`call_sheet_status`, `cast_status_code`, `distribution_channel`, `int_ext`,
`day_night` all still exist in `pg_type` after the "full" downgrade.
Re-running `alembic upgrade +1` from base then fails outright:

```
sqlalchemy.exc.ProgrammingError: (psycopg.errors.DuplicateObject) type "production_status" already exists
[SQL: CREATE TYPE production_status AS ENUM ('PREP', 'SHOOTING', 'WRAPPED')]
```

### 2. `5baf4c476bc7` ("production members and roles") — downgrade leaves 1 orphaned enum type

Same root cause, smaller scope: `downgrade()` runs `op.drop_table
('production_members')`, which drops the table but not the `production_role`
enum type the table's `role` column created. Re-upgrading fails the same way:

```
sqlalchemy.exc.ProgrammingError: (psycopg.errors.DuplicateObject) type "production_role" already exists
[SQL: CREATE TYPE production_role AS ENUM ('OWNER', 'EDITOR', 'VIEWER')]
```

Both are the same, well-known Alembic/SQLAlchemy autogenerate gap: a
`sa.Enum(..., name=...)` column implicitly creates a named Postgres type on
`create_table`/`add_column`, but `drop_table`/`drop_column` never implicitly
drops that type — it must be dropped explicitly (`op.execute('DROP TYPE
...')` or `sa.Enum(...).drop(op.get_bind())`) in `downgrade()`, and neither
migration does. Grepped all 19 files for `sa.Enum(`: only these two create
one; no other migration has this specific gap.

### 3. `9520a7babf8c` ("crew head of department, revision head of day") — downgrade crashes outright

This one does not just leave stale state — it fails immediately, every
time, with no successful downgrade possible via Alembic at all:

```python
def upgrade() -> None:
    op.add_column('call_sheet_revisions', sa.Column('head_of_day_crew_member_id', sa.Uuid(), nullable=True))
    op.create_foreign_key(None, 'call_sheet_revisions', 'crew_members', ['head_of_day_crew_member_id'], ['id'])
    ...

def downgrade() -> None:
    op.drop_column('crew_members', 'is_head_of_department')
    op.drop_constraint(None, 'call_sheet_revisions', type_='foreignkey')
    ...
```

`op.create_foreign_key(None, ...)` lets Postgres auto-name the constraint
(`call_sheet_revisions_head_of_day_crew_member_id_fkey`), which is fine for
`upgrade()`. But `downgrade()`'s `op.drop_constraint(None, ...)` passes
`None` as the name to drop — Alembic never resolves `None` to the real
auto-generated name, so SQLAlchemy raises at DDL-compile time, before
touching the database:

```
sqlalchemy.exc.CompileError: Can't emit DROP CONSTRAINT for constraint
ForeignKeyConstraint(...); it has no name
```

This is the template warning ("# ### commands auto generated by Alembic -
please adjust! ###") that nobody adjusted before merging — `None` is a
placeholder, not a valid name, for `drop_constraint`.

## Everything else: clean

The remaining 16 migrations (including both merge revisions,
`1a23c1644d06` and `1674568dd98c`, both no-op `pass`/`pass` bodies) round-trip
with an identical schema fingerprint before downgrade and after the matching
re-upgrade. Verified individually: `7feea1cfc0e6`, `e5c7a2f9d1b8`,
`d8f4b1c9a2e6`, `22f098e3dc1d`, `f3b8d6e1a9c7`, `e2a7c5d9f4b6`,
`d1f6b4c8e3a5`, `c9e5a3b7d2f4`, `b8d4f2a6c1e3`, `a7c3e9f1b2d4`,
`1674568dd98c`, `1a23c1644d06`, `b6a1e5f3d7c2`, `d353e6845c8e`,
`c2a1f9e7b3d4`, `931c2ab3ce65`.

## Separate finding: `alembic downgrade -1`/`upgrade +1` can't walk straight through a merge point

Not a bug in any single migration — a tooling/process gap in the literal
"`downgrade -1` then `upgrade +1`, nineteen times" procedure this item's own
`dod` names. The history has two real branch/merge points
(`c2a1f9e7b3d4` branches into `d353e6845c8e` and the merge `1a23c1644d06`;
`1674568dd98c` merges `1a23c1644d06` and `b6a1e5f3d7c2`). Relative `-1`/`+1`
navigation raises `Ambiguous walk` there — e.g. from `1674568dd98c`:

```
$ alembic downgrade -1
ERROR [alembic.util.messaging] Ambiguous walk
FAILED: Ambiguous walk
```

Explicit revision targets (`alembic downgrade 1a23c1644d06`,
`alembic downgrade d353e6845c8e`, etc.) work correctly and were used to
carry the walk through both merge points — that's how all 19 migrations
got individually exercised despite this. Worth knowing for whoever next
needs to downgrade past one of these two points by hand (e.g. a future
backup-restore drill, FR-177): use an explicit revision, not `-1`.

## Conclusion

Per this item's own failure case: a real downgrade bug, not qa's to patch
invisibly inside a verification item. Filed as **FR-179** (tech-lead) to fix
the three `downgrade()` bodies above (drop the enum types explicitly in
`0ea2247026ef`/`5baf4c476bc7`; replace the two `None` placeholders in
`9520a7babf8c` with the real constraint names) and re-run this exact walk
to confirm all 19 round-trip clean. No code in `backend/` was changed by
this item — the bugs are recorded, not silently fixed.
