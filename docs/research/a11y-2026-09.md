# Accessibility pass, 2026-09-22 (FR-63)

axe-core 4.10.2 through Playwright at iPhone width (390 px), on the screens a crew member and an AD
actually use. Test: `frontend/tests/test_a11y.py` — it fails on any **serious** or **critical**
violation and prints the rest (run with `-s`), so a regression fails CI.

Screens covered: the crew's sheet (demo, English and Czech), a crew member's personal link, the
editor's day screen (published, with scenes, personal calls, seen-by and share blocks), the editor's
Crew tab (with imports open), the landing page, the privacy note.

## Result

**0 violations at any impact level on all seven screens**, after the fixes below.

## What axe found and what was done

| Rule | Impact | Where | Fix |
|---|---|---|---|
| `color-contrast` | serious | 41 nodes on the sheet, 13 in the editor: every hint, meta line, label, date, the struck-through "before" value in the revision diff, the muted parts of the status line | `--muted` was `#7a746b` — **4.22:1** on the paper background, under the 4.5:1 AA minimum for text this size. Now `#6e685f`: **5.02:1** on paper, 4.6:1 on the shaded panels, 5.5:1 on white. Same token in `landing.css`. |
| `color-contrast` | serious | 7 nodes: the initials in an avatar with no photo | `.avatar-fallback` drew `--muted` on the `--rule` chip (3.6:1). Now `--ink-2`: **6:1**. The initials are decorative (the name is next to them) but they are still text on screen. |
| `landmark-one-main` | moderate | every page | The sheet, the editor, sign-in, connect, the landing and the privacy note each have a `<main>` now. |
| `region` | moderate | `#status`, `#sheet`, `.privacy-line`, `.tabs`, and 20 nodes on the landing | All of it was content outside any landmark; the `<main>` above covers it. |

## Zoom / reflow, 2026-09-23 (FR-73)

WCAG 1.4.10 (Reflow): content must not require horizontal scrolling at a viewport 320 CSS pixels wide
— the standard equivalent of 400% browser zoom on a 1280px reference width, itself the accepted proxy
for the mobile case (a phone already at a narrow width with the system text size turned up). Test:
`frontend/tests/test_reflow.py`, resizing the viewport to 320×800 rather than driving a real OS zoom
control (the technique WCAG's own Understanding doc names first). Two checks per screen: no
page-level horizontal scroll (`scrollWidth` vs `clientWidth` on `<html>`), and no individual element
whose own content is wider than its box (a proxy for clipped text; true visual overlap was not probed
— nothing in this codebase's CSS uses absolute or negative-margin positioning for text, only
grid/flex/block flow, so overlap is not a realistic risk at this width the way clipping is).

**Real finding, fixed in this PR**: the mobile schedule table (`@media (max-width: 560px)` in
`styles.css`) folds six desktop table columns into a two-line grid per scene. The Day/Night cell
(`td.dn`) inherited the desktop table's `width: 5ch` and `padding-right: 12px` — sized for a column
boundary that no longer exists once it's the last cell in its grid row. "DAY" fit inside that box at
320px; "NIGHT" (2 letters longer, plus letter-spacing) clipped by 3px. Not user-typed content — DAY
and NIGHT are our own fixed labels — so this was ours to fix, not document as a content limitation:
`td.dn` now gets `width: auto; padding-right: 0` inside the mobile query, letting the grid area's own
(ample) width govern it. Verified both values render without clipping at 320px after the fix.

**Checked and clean**: the crew sheet demo (English and Czech) at 320px, after the fix above.

**User-typed-content case, per this item's own failure case**: published a real revision with a scene
`Set` field containing a long compound location name with no spaces to break on
(`EXT. NÁDRAŽÍ-VRŠOVICE-DEPO-KOLEJIŠTĚ-SEVEROVÝCHODNÍ-VJEZD-U-SEMAFORU`, the kind of thing an AD
might actually paste from a permit document) and opened the resulting personal link at 320px: no
clipping and no page-level horizontal scroll — the `set` grid area is `1fr`-sized and the browser
wraps the text across lines rather than forcing scroll. No failure to document here; the layout
already handles this case correctly. Per FR-63's own precedent, had a real clipping case turned up on
user-typed text, the finding would be recorded here as a documented limitation, not "fixed" by
truncating the AD's own text.

## Accessible name / visible label mismatch, 2026-09-24 (FR-82)

`label-content-name-mismatch` (axe): the accessible name (from `aria-label`) must contain the
control's own visible text, so a voice-command or braille-display user who read the printed label
out loud can still activate the control by that name. FR-71's Lighthouse run flagged two shapes,
confirmed in `docs/research/lighthouse-pilot-scale.json` and reproduced directly against axe-core
(`frontend/node_modules/axe-core`) in an isolated Playwright probe before touching any code, to
confirm the actual cause rather than guessing at the algorithm:

- **`#langToggle`** (public sheet and editor mastheads): `aria-label` held a translated *action*
  sentence ("Přepnout do češtiny" / "Switch to English") that does not literally contain the printed
  *target-language name* ("Čeština" / "English") — worst on the Czech direction, where "Čeština"
  (nominative) versus "do češtiny" (genitive) differ by more than case folding. **Fix**: dropped
  `aria-label` entirely — the printed target-language name is now the accessible name too, so it can
  never drift from what's on screen — and moved the old action sentence to `title` as a hover
  tooltip, the dod's own second option. `frontend/src/App.tsx` and `frontend/src/editor/EditorApp.tsx`
  both had their own copy of this button; both fixed.
- **`.contact-btn.copy`** (`ContactCopyButton`, shared by every Copy-number button on the public
  sheet and personal links — 13 instances on the FR-52 pilot-scale demo): the ⧉ icon was a real DOM
  text node (`<span aria-hidden="true">⧉</span>`) immediately before the word "Copy"/"Copied". Even
  though `aria-hidden` correctly excludes it from the *accessible* name, it is still part of the
  control's *visible* text (sighted users see it), and axe's rule compares against visible text, not
  the accessible-name tree — so the glyph character itself was the literal mismatch, confirmed by the
  probe: putting the exact same glyph inside `aria-label` still failed once whitespace didn't line up
  byte-for-byte. **Fix**: the icon is now a CSS `::before` on `.contact-btn.copy` (`styles.css`),
  never a DOM text node, so it cannot be visible-but-unnamed again; `aria-label` (`"Copy {name}"` /
  `"Copied {name}"`) is unchanged, since it already spoke the real button text plus the context (whose
  number) a repeated "Copy" label alone would have lost for a screen-reader user with 13 of them on
  one screen. This is the shared component every per-contact Copy button renders from, so the fix
  cannot regress per-instance (the item's own failure case).
